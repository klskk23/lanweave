# Feature Specification: Swagger / OpenAPI 文档页面

**Feature Branch**: `029-swagger-ui`

**Created**: 2026-06-10

**Status**: Draft

**Input**: User description: "服务端暴露 Swagger / OpenAPI 文档页面（切片 029 swagger-ui，对应 TODO.md Server MEDIUM「暴露 swagger 页面」）。需求：lanweaved 服务端提供一份完整描述现有控制面 REST API 的 OpenAPI 3 文档（覆盖 /api/v1 下全部端点），包含请求/响应 schema、bearer JWT 安全方案标注（公开端点除外）、各端点的错误码。同时服务端提供可交互的 Swagger UI 页面渲染该文档，方便联调与第三方接入。该页面可通过配置开关控制是否暴露。文档必须与实际 API 行为保持一致。不做：不改变任何现有 API 行为；不做 API 版本化改造；客户端零改动。"

### Session 2026-06-10

- Q: OpenAPI 文档里的端点描述文字（summary/description、错误码含义）用什么语言？ → A: 英文（与服务端现有英文错误消息、代码注释口径一致，面向第三方接入与工具链）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 第三方开发者通过文档页面探索并调用 API (Priority: P1)

一位要为 lanweave 写自动化脚本（或自研客户端）的开发者，在浏览器打开服务器的文档页面，看到控制面全部 API 端点的清单：每个端点的方法、路径、请求体字段、响应结构、可能的错误码，以及哪些端点需要登录凭证。他在页面上输入自己的访问令牌，直接对真实服务器发起一次调用（如「列出我的节点」），在页面内看到真实响应——全程无需阅读源码或抓包。

**Why this priority**: 这是本切片的核心价值——把「API 形状只存在于源码里」变成「任何持有服务器地址的开发者都能自助联调」。没有这一条，其余需求无意义。

**Independent Test**: 启动服务端，浏览器访问文档页面，确认全部端点可见；用有效令牌在页面内完成一次认证调用并得到真实响应。

**Acceptance Scenarios**:

1. **Given** 服务端正常运行且文档功能开启，**When** 用户在浏览器访问文档页面，**Then** 页面列出 `/api/v1` 下全部现有端点（healthz、login、register、refresh、logout、me、server、nodes 的增/删/查、zones 的创建/列表/join/leave/members、zone owner 的改密/删 zone/踢人、admin 的邀请码创建/列表与删用户），每个端点可展开查看请求字段与响应结构。
2. **Given** 用户已在文档页面填入有效的访问令牌，**When** 他对一个需认证端点（如列出节点）发起「试一试」调用，**Then** 页面显示服务器的真实响应（状态码与 JSON 内容）。
3. **Given** 用户查看任一端点的文档，**When** 该端点存在业务错误（如设备超限、zone 名被占用），**Then** 文档列出对应的错误码与含义，与服务器实际返回一致。
4. **Given** 用户查看需要管理员权限的端点（admin 邀请码/删用户），**Then** 文档明确标注其权限要求高于普通登录。

---

### User Story 2 - 运维通过配置开关控制文档暴露 (Priority: P2)

一位运维在生产环境部署 lanweave，不希望对外暴露 API 文档。他在服务端配置文件中关闭文档开关并重启服务，文档页面与文档数据从外部彻底不可见；需要联调时再打开。

**Why this priority**: 文档默认开启换取开箱联调体验，但生产环境必须保留「关掉」的能力，否则该功能会成为部署阻碍。

**Independent Test**: 配置关闭开关后重启服务，访问文档路径得到与访问任意不存在路径相同的「未找到」响应；其余 API 全部正常。

**Acceptance Scenarios**:

1. **Given** 配置中未写文档开关（缺省），**When** 服务启动，**Then** 文档页面可访问（默认开启）。
2. **Given** 配置中显式关闭文档开关，**When** 外部访问文档页面或文档数据路径，**Then** 得到与访问任意未知路径完全相同的「未找到」响应（不暴露「文档存在但被关闭」的信息）。
3. **Given** 文档开关关闭，**When** 客户端照常使用全部业务 API，**Then** 行为与开关开启时完全一致（开关只影响文档，不影响业务）。

---

### User Story 3 - 工具链消费机器可读的 API 描述文件 (Priority: P3)

一位开发者想用代码生成器或 API 测试工具对接 lanweave。他直接下载服务器暴露的机器可读 API 描述文件（OpenAPI 3 格式），导入自己的工具链生成客户端代码或测试集合。

**Why this priority**: 文档页面解决「人看」，描述文件解决「机器用」；后者依附前者（页面本身就靠这份文件渲染），单独成本极低但显著扩大适用面。

**Independent Test**: 直接请求描述文件路径，得到一份语法合法、可被标准 OpenAPI 工具解析的 OpenAPI 3 文档。

**Acceptance Scenarios**:

1. **Given** 文档功能开启，**When** 用户请求 API 描述文件，**Then** 返回一份语法合法的 OpenAPI 3 文档，可被标准校验工具零错误解析。
2. **Given** 该描述文件，**When** 与服务器实际路由对比，**Then** 文件中的端点集合与服务器实际注册的端点集合完全一致（不多、不少、方法与路径一致）。

---

### Edge Cases

- 文档开关关闭时，文档相关路径必须返回与未知路径**完全相同**的响应（状态码与响应体），避免探测者借差异确认服务身份与功能开关状态。
- 服务端运行在明文 HTTP 模式（021，TLS 由反向代理终止）并挂在反代路径后时，文档页面加载其所需资源、以及「试一试」调用，必须仍指向正确的服务器地址（不得硬编码绝对地址导致反代后跳错）。
- 文档页面与描述文件受与业务 API 相同的全局限流约束，恶意刷文档不会绕过限流。
- 文档与描述文件内不得包含任何真实机密（真实邀请码、真实令牌、密码、私钥）；示例值一律使用显式虚构占位。
- 未来新增/修改/删除端点而忘记同步文档时，必须有自动化手段在合入前暴露这种漂移（具体机制留 plan 阶段，但「会被自动发现」是本 spec 的硬要求）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 服务端 MUST 提供一份 OpenAPI 3 格式的机器可读 API 描述文件，覆盖 `/api/v1` 下全部现有端点（当前共 21 个操作：healthz、login、register、refresh、logout、me、server、nodes×3、zones×5、zone-owner×3、admin×3）。
- **FR-002**: 描述文件中每个端点 MUST 包含：请求体字段及约束、成功响应结构、该端点实际可能返回的错误码及含义（错误码全集：`validation_error`、`unauthorized`、`forbidden`、`not_found`、`method_not_allowed`、`rate_limited`、`internal_error`、`invalid_credentials`、`invalid_refresh_token`、`invite_invalid`、`username_taken`、`pubkey_taken`、`node_name_taken`、`zone_name_taken`、`invalid_zone_or_password`、`device_limit_reached`、`zone_limit_reached`、`pool_exhausted`、`last_admin`、`cannot_delete_self`，各端点只列自己实际会返回的子集）。
- **FR-003**: 需认证端点 MUST 标注 bearer 令牌安全方案；公开端点（healthz、login、register、refresh、logout）MUST 标注为无需认证；admin 端点 MUST 额外标注管理员权限要求。
- **FR-004**: 服务端 MUST 提供一个可交互的文档页面，渲染上述描述文件，支持：浏览全部端点、填入 bearer 令牌、对真实服务器发起调用并展示响应。
- **FR-005**: 文档功能 MUST 由服务端配置文件中的单一开关控制；**缺省（不写该键）= 开启**；显式关闭后文档页面与描述文件均不可访问。
- **FR-006**: 开关关闭时，访问文档相关路径 MUST 返回与访问任意未知路径完全相同的响应。
- **FR-007**: 文档页面 MUST 在 HTTPS 模式与明文 HTTP 模式（021 反代场景）下均可正常工作；页面资源与「试一试」调用不得依赖硬编码的绝对服务器地址。
- **FR-008**: 文档页面 MUST 完全自包含于服务端（不依赖外部互联网资源加载），保证内网/离线部署可用。
- **FR-009**: 描述文件与文档页面中 MUST NOT 出现任何真实机密；示例值 MUST 为显式虚构占位。
- **FR-010**: 描述文件所列端点集合 MUST 与服务器实际注册路由保持一致，且这种一致性 MUST 由自动化测试保证（新增/删除端点而未同步文档时测试失败）。
- **FR-011**: 本切片 MUST NOT 改变任何现有 API 的路径、请求/响应格式与行为；客户端零改动。
- **FR-012**: 文档相关路径 MUST 与业务 API 受同一全局限流约束。
- **FR-013**: 描述文件内全部人类可读文字（端点 summary/description、字段说明、错误码含义）MUST 使用英文，与服务端现有错误消息语言一致；不提供中文或双语版本。

### Key Entities

- **API 描述文件**: 一份 OpenAPI 3 文档，是「API 形状」的可发布表达；关键属性：端点集合、各端点请求/响应 schema、安全方案标注、错误码枚举。与实际路由的一致性受自动化测试保护。
- **文档页面**: 渲染描述文件的交互式网页；关键属性：端点浏览、令牌填入、试调用。自包含、无外部网络依赖。
- **文档开关**: 服务端配置中的布尔开关；缺省=开启；关闭时文档路径表现为「不存在」。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一位从未接触过本项目源码的开发者，仅凭服务器地址与一个账号，能在 10 分钟内通过文档页面完成「登录拿令牌 → 列出自己的节点」的完整调用链。
- **SC-002**: 描述文件覆盖率 100%：文件端点集合与服务器实际路由逐一对应，自动化比对零差异。
- **SC-003**: 关闭开关后，从外部无法以任何方式区分「文档功能被关闭」与「该路径从不存在」。
- **SC-004**: 全部现有自动化测试在本切片合入后保持绿色（现有 API 行为零回归）。
- **SC-005**: 文档页面在无外网访问的隔离环境中完整可用（页面渲染与试调用均正常）。

## Assumptions

- 文档页面开启时**无需登录即可浏览**：描述文件只含 API 形状、不含数据，且运维已握有开关；为「试一试」强加登录会破坏「拿邀请码前先看文档」的接入流程。
- 文档暴露路径为服务端保留路径（如 `/api/docs` 一类），具体路径在 plan 阶段定；不与现有 `/api/v1/*` 任何端点冲突。
- 「文档与实际行为一致」的强制粒度为：**端点集合（方法+路径）一致性必须自动化**；字段级 schema 漂移依赖代码评审与文档生成机制（具体机制 plan 阶段决策）。
- 默认开启的取舍已被接受：描述文件不含机密，暴露面仅为「API 形状」；生产环境可显式关闭（用户已确认默认开启）。
- 本切片不修改 DESIGN.md 的安全立场：控制面鉴权、限流、TLS 口径均不变；如 plan 阶段发现需在 DESIGN.md §11 登记「默认暴露 API 形状」为已接受风险，则同 PR 修订。
- Windows 客户端完全不感知本功能。
