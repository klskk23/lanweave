# Feature Specification: tunnel-auto-reconnect

**Feature Branch**: `028-tunnel-auto-reconnect`

**Created**: 2026-06-08

**Status**: Draft

**Input**: User description: "客户端隧道握手陈旧自愈重连：health goroutine 每 15s 检查 wg 最后握手时间，已连接但超 240s 阈值自动重连；desiredConnected 仅内存态，重连失败每 15s 重试到底；wg 源端口为 OS 随机临时端口（已满足，仅文档化）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 链路静默断掉后自动恢复连接 (Priority: P1)

用户已经连上 VPN 并在正常使用。途中链路在用户无感知的情况下失效——服务器重启、NAT 映射被回收、家里 WiFi 抖动、笔记本休眠后唤醒。今天的客户端会一直显示「已连接」、流量却早已停摆，用户要么盯着发现不对、要么手动断开再重连才能恢复。本故事让客户端自己发现连接已死并自动重连，把「假在线」变成「自愈」。

**Why this priority**: 这是整个特性存在的理由,也是唯一对用户有独立价值的核心能力。没有它,客户端在最常见的掉线场景里会长期停在错误的「已连接」状态,流量不通却不自知。单独交付这一条即构成可用的 MVP。

**Independent Test**: 连上后在外部令链路失效（如阻断到服务器的可达性），不做任何手动操作，观察客户端在阈值时间内自行进入「正在连接」并在链路恢复后回到「已连接」、流量恢复——全程无需用户点击。

**Acceptance Scenarios**:

1. **Given** 客户端已连接且链路正常，**When** 链路失效导致握手停止更新超过陈旧阈值，**Then** 客户端自动发起重连，无需用户操作。
2. **Given** 客户端因链路失效正在自动重连且链路此时已恢复，**When** 一次重连尝试完成，**Then** 客户端回到「已连接」、流量恢复、界面状态转为正常连接态。
3. **Given** 客户端正在自动重连但链路尚未恢复（重连尝试失败），**When** 失败后等待一个轮询周期，**Then** 客户端再次发起重连，并持续重试直到连回或用户主动干预。
4. **Given** 客户端已连接且链路正常、握手按预期刷新，**When** 持续观察，**Then** 客户端不发起任何重连（不误判健康连接）。

---

### User Story 2 - 重连期间的界面反馈与用户可中止 (Priority: P2)

当客户端在后台自愈重连时，用户需要从界面看出「正在恢复」而不是「已失败、要我自己处理」，并且必须能够随时叫停这个后台重试循环（例如用户决定先不连了）。本故事定义自愈过程中用户看到什么、以及如何重新拿回控制权。

**Why this priority**: 没有清晰反馈,后台自愈对用户是黑箱:界面要么误显示「已连接」(流量却不通)、要么误显示「失败」(其实正在重试)。更关键的是,若重试中没有可用的中止入口,用户会陷入一个停不下来的后台循环。此故事建立在 P1 之上,提供必要的可观察性与控制权,但 P1 的自愈逻辑本身可独立成立。

**Independent Test**: 在自愈重连进行中观察界面状态指示与主操作按钮，确认显示「正在恢复」语义且主按钮提供中止入口；点击中止后客户端停止重连并停留在断开状态。

**Acceptance Scenarios**:

1. **Given** 客户端正在自动重连或失败后等待重试，**When** 用户查看界面，**Then** 连接状态显示为「正在连接」语义（表达正在恢复），而非「连接失败」红色错误态。
2. **Given** 客户端正在自动重连或重试，**When** 用户查看主操作按钮，**Then** 按钮提供「断开」动作。
3. **Given** 客户端正在自动重连或重试，**When** 用户点击「断开」，**Then** 客户端立即停止后台重试、回到断开状态，且此后不再自动重连（直到用户重新手动连接）。
4. **Given** 自动重连/重试过程进行中，**When** 全过程发生，**Then** 客户端不弹出任何对话框或打扰式提示（全程静默，仅更新状态行与按钮）。

---

### User Story 3 - 自愈只维持「用户已建立的连接」，不擅自建立连接 (Priority: P2)

自动重连必须严格限定职责：它只负责把一条「用户曾经成功连上、之后掉了」的连接拉回来；它不接管「建立连接」，也不在用户没有连接意图时擅自连上。本故事钉死自愈的边界，避免用户手动断开后被强行连回、或手动连接失败后被无限重试、或应用一启动就替用户连上。

**Why this priority**: 这是自愈行为的安全边界。缺了它,P1 的自愈逻辑会在错误的时机触发——用户主动断开却被连回、连接失败却被无限重试、开机即自动连接——这些都是明确的反预期行为。它与 P2 的反馈/中止同等重要,共同约束 P1 的触发条件。

**Independent Test**: 分别验证三种「不应自愈」的情形——用户主动断开后、用户手动连接失败后、应用重启后——客户端均保持断开、不发起任何自动重连。

**Acceptance Scenarios**:

1. **Given** 客户端已连接，**When** 用户主动点击「断开」，**Then** 客户端断开并保持断开，不被自动重连连回。
2. **Given** 客户端处于断开态，**When** 用户手动发起连接但连接失败，**Then** 客户端保持断开，不进入自动重试循环（自愈不接管「建立连接」）。
3. **Given** 用户上次会话曾成功连接，**When** 用户退出并重新启动应用，**Then** 客户端启动后处于断开态、不自动连接（连接意图不跨重启保留）。
4. **Given** 用户主动发起的连接正在进行中（尚未成功），**When** 自愈检查在此刻运行，**Then** 自愈不介入这次进行中的手动连接（不与之竞争）。

---

### Edge Cases

- **手动断开与自动重连竞争**：用户在一次自动重连尝试正在进行（尚未返回结果）时点击「断开」——即便该重连尝试随后恰好成功，最终结果也必须是「断开」，绝不能出现连接被「复活」。用户的断开意图始终优先。
- **重连尝试期间的入站可达性**：自愈在重连时会先拆除旧隧道。在「已拆除、尚未连回」的窗口内没有任何隧道存在，此时主机入站放行规则必须处于关闭状态（不放行不存在的隧道），连回后自动恢复——与用户手动断开时的处理一致。
- **长时间外网不通**：链路失效持续数分钟（如长时间断网）。客户端应保持「正在恢复」状态并持续按固定节奏重试，外网恢复后的下一个重试周期内连回，期间不放弃、不退避加速、不进入永久失败态。
- **健康连接的边界**：握手时间恰好接近但未超过陈旧阈值时，不得触发重连；恰好超过阈值时，必须触发。
- **重连自身不重叠**：自愈检查按固定周期运行，单次重连尝试耗时短于检查周期，保证同一时刻不存在两个并发的重连尝试。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 客户端 MUST 在连接处于「已连接」状态时，周期性地检查本端 VPN 最近一次握手的时间，以判断链路是否仍然存活。
- **FR-002**: 当连接处于「已连接」状态且「当前时间与最近握手时间之差」超过陈旧阈值时，客户端 MUST 判定该连接已失活并自动发起重连。
- **FR-003**: 陈旧阈值 MUST 为 240 秒。
- **FR-004**: 活性检查 MUST 按 15 秒的周期运行。
- **FR-005**: 活性检查与自动重连 MUST 不阻塞客户端既有的、面向服务器的节点列表刷新（两者互不拖慢）。
- **FR-006**: 客户端 MUST 维护一个「用户连接意图」状态：用户手动连接成功时置为「希望连接」，用户主动断开时置为「不希望连接」。
- **FR-007**: 「用户连接意图」状态 MUST 仅存在于运行期（不持久化）；应用重启后默认为「不希望连接」，即启动后不自动连接。
- **FR-008**: 自动重连 MUST 仅在「用户连接意图」为「希望连接」时发生；意图为「不希望连接」时一律不触发自动重连。
- **FR-009**: 用户主动发起的连接若失败，MUST NOT 触发自动重试（自愈只维持已建立的连接，不接管建立连接）。
- **FR-010**: 当一次自动重连尝试未能恢复连接时，客户端 MUST 在下一个检查周期再次尝试，并持续重试直至连接恢复或用户主动断开；重试节奏 MUST 为固定周期，MUST NOT 采用指数退避。
- **FR-011**: 用户主动断开 MUST 立即停止任何正在进行或等待中的自动重连，并使连接进入并保持断开状态。
- **FR-012**: 所有连接状态切换（用户手动连接、手动断开、自动重连）MUST 串行化，任一时刻至多一个连接尝试在进行；用户的断开意图 MUST 始终优先——即便一次重连尝试恰好成功，若用户在此期间已表达断开意图，最终结果 MUST 为断开（不得出现已断开的连接被重连尝试「复活」）。
- **FR-013**: 在自动重连或失败后等待重试期间，客户端的连接状态 MUST 向用户呈现为「正在连接」语义（表达正在恢复），而非「连接失败」错误态。
- **FR-014**: 在自动重连或重试期间，主操作按钮 MUST 提供「断开」动作，使用户能够中止后台重试。
- **FR-015**: 整个自动重连与重试过程 MUST 全程静默——不弹出对话框或打扰式提示，仅更新连接状态指示与主操作按钮。
- **FR-016**: 自动重连过程 MUST 维持既有的主机入站放行规则不变量（规则存在当且仅当用户开启了入站放行开关且隧道实际已连接）；在「已拆除旧隧道、尚未连回」的重连窗口内，入站放行规则 MUST 处于关闭状态，连回后自动恢复。
- **FR-017**: 客户端每次发起 VPN 连接所使用的本端源端口 MUST 为操作系统分配的随机临时端口；该行为为既有保证，本特性 MUST NOT 改为固定端口（仅以文档固化此依赖，防止回退）。

### Key Entities

- **连接意图（Desired Connection State）**：表示用户当前是否希望保持连接的运行期状态。取值为「希望连接 / 不希望连接」。手动连接成功置真，手动断开置假；不跨应用重启保留。它是判断「是否应自动重连」的唯一依据。
- **握手陈旧度（Handshake Staleness）**：由「当前时间」与「本端 VPN 最近一次成功握手时间」之差导出的派生量，用于判断已建立的连接是否仍然存活。超过陈旧阈值即视为失活。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 连接在使用中失活后，客户端在无任何用户操作的情况下自动恢复连接；从链路恢复可用到客户端重新显示「已连接」，在一个检查周期（≤15 秒）内完成。
- **SC-002**: 健康、握手正常刷新的连接在持续观察下触发自动重连的次数为 0（无误判重连）。
- **SC-003**: 用户主动断开后，连接保持断开；在后续观察窗口内被自动重连连回的次数为 0。
- **SC-004**: 用户手动连接失败后，客户端不进入自动重试；后续观察窗口内自动发起的连接尝试次数为 0。
- **SC-005**: 在一次自动重连尝试正在进行时用户点击「断开」，最终连接状态 100% 为断开（连接被「复活」的发生率为 0）。
- **SC-006**: 自愈重连进行期间，面向服务器的节点列表刷新不被延迟到超过其正常周期之外（自愈不拖慢既有轮询）。
- **SC-007**: 应用重启后，客户端处于断开态、不自动连接的比例为 100%。
- **SC-008**: 连续两次连接所使用的本端源端口为不同的随机临时端口。

## Assumptions

- 客户端为单机单隧道模型（一台机器一条 VPN 隧道），本特性不涉及多隧道。
- 「最近握手时间」可从本端 VPN 引擎读取，作为链路存活的权威信号；持续保活机制使健康连接的握手按预期周期刷新。
- 本特性为**纯客户端**改动，不涉及任何服务端协议或行为变更。
- 「开机/启动自动连接」明确不在本特性范围内，属另行评估的独立能力。
- 主机入站放行开关及其规则生命周期由既有能力（slice 018）提供，本特性复用之，仅要求自动重连遵守同一不变量。
- 源端口随机化为既有实现的天然结果（每次连接由操作系统分配随机临时端口），本特性不新增端口随机化逻辑，仅文档化并以验收守护其不被回退。
- 自愈检查复用既有 15 秒轮询节奏；单次重连尝试的耗时短于该周期，从而保证重连尝试不自相重叠。
