# Feature Specification: client-session-persist-fix

**Feature Branch**: `019-client-session-persist-fix`

**Created**: 2026-06-07

**Status**: Draft

**Input**: User description: "019 — 修复客户端：向导首次登录进入面板后再次提示登录输入账号密码；注册后还需要手动登录"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 首次设置完成后直接进入主面板 (Priority: P1)

新用户或换机用户在首次启动客户端时走设置向导：填服务器地址 → 选择「登录已有账号」或「创建新账号」并填好凭据 → 命名本机设备 → 完成。设置一旦成功，用户应**直接进入主面板**，不应被要求再输入一次账号密码。

**Why this priority**: 这是用户最直接撞到的阻断性体验缺陷——刚刚在向导里登录/注册过，进面板却又被要求登录一次，让人怀疑前面的操作是否失败。修掉它是本切片的核心价值，单独交付即可消除主要困惑。

**Independent Test**: 在一台干净设备上完整走一遍向导（分别用「登录」与「创建账号」两条路径各测一次），确认完成后落在主面板且全程只输入一次凭据、不出现第二个登录框。

**Acceptance Scenarios**:

1. **Given** 一台未设置过的设备，**When** 用户在向导里用已有账号成功登录并完成设备命名，**Then** 用户直接进入主面板，不再被要求输入账号密码。
2. **Given** 一台未设置过的设备，**When** 用户在向导里用邀请码创建新账号并完成设备命名，**Then** 用户直接进入主面板，不再被要求单独登录。
3. **Given** 用户刚通过向导完成设置进入主面板，**When** 面板加载设备与 zone 列表，**Then** 这些需要登录态的操作直接成功，无需用户重新认证。

---

### User Story 2 - 再次启动复用已保存的会话 (Priority: P2)

已完成设置的用户关闭并重新打开客户端。只要上次的登录会话仍然有效，应直接进入主面板，不必重新输入账号密码。

**Why this priority**: 与 US1 同源——设置阶段建立的会话若被持久保存，冷启动自然复用。它把「不重复登录」的体验从首次设置延伸到每次日常启动，价值高但属于核心修复的自然延伸。

**Independent Test**: 完成设置后关闭客户端再重新打开，确认在会话有效期内直接进入主面板、无登录框。

**Acceptance Scenarios**:

1. **Given** 已设置且会话仍有效的设备，**When** 用户重新启动客户端，**Then** 用户直接进入主面板，不被要求登录。
2. **Given** 已设置但会话已过期或被服务器拒绝的设备，**When** 用户重新启动客户端，**Then** 系统提示用户重新登录（保留现有的失效再登录行为）。

---

### User Story 3 - 取消或失败的设置不留残余凭据 (Priority: P3)

用户在向导中途取消，或设置过程中途失败。设备应回到「未设置」的干净状态，本地不残留任何可用的登录凭据或半成品设置记录。

**Why this priority**: 安全与一致性兜底。若设置阶段就持久化了会话，必须保证取消/失败路径把它和其它本地状态一并清掉，避免留下「有登录凭据却无完整设置」的孤儿态。

**Independent Test**: 在向导任一步取消（或制造一次设置失败），随后重启客户端，确认应用从设置向导的第一步开始、且没有任何残留登录态。

**Acceptance Scenarios**:

1. **Given** 用户在向导某一步点了取消，**When** 用户重新启动客户端，**Then** 应用从设置向导第一步开始，本地无残留凭据或设置记录。
2. **Given** 设置在「设备注册」阶段失败，**When** 系统提示错误，**Then** 本地不残留可用登录凭据（重试或重启都从干净态开始）。

### Edge Cases

- 设置全部成功、但在「保存会话凭据」这最后一步本身失败时如何处理？（应作为可重试的设置错误暴露，不静默把用户带入一个其实未保存会话、随即又要求登录的面板。）
- 会话在向导完成与主面板首次拉取数据之间被服务器判失效时如何处理？（按既有失效路径提示重新登录，不崩溃、不静默卡住。）
- 同一台设备上一个账号已留有有效会话、用户未登出又重新走向导并中途取消：取消后不应残留上一账号的会话凭据。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 首次设置（登录已有账号或创建新账号）成功后，系统 MUST 直接将用户带入主面板，且 MUST NOT 再次要求其输入账号密码。
- **FR-002**: 系统 MUST 持久保存首次设置阶段建立的已认证会话，使其在向导结束、构建主面板后依然有效可用。
- **FR-003**: 在后续每次启动时，系统 MUST 复用已持久保存且仍然有效的会话，不再要求用户输入凭据。
- **FR-004**: 当已保存的会话已过期或被服务器拒绝时，系统 MUST 提示用户重新登录（保留现有失效再登录行为不变）。
- **FR-005**: 会话凭据 MUST 仅在整个首次设置**完整成功后**（账号已认证、设备已注册、本地设置记录已写入）才被持久保存，避免出现「已保存可用会话但无对应设备设置记录」的中间态。
- **FR-006**: 当首次设置被取消或失败时，系统 MUST 清除本地保存的会话凭据与设置记录，使设备回到干净的未设置状态。
- **FR-007**: 持久保存的会话凭据 MUST 存入操作系统安全存储，绝不写入明文本地设置文件或日志（与既有「设备私钥仅存安全存储」的安全不变量一致）。

### Key Entities *(include if feature involves data)*

- **会话凭据 (Session credential)**：代表当前已登录用户的认证会话，使后续受保护操作免于重复登录。属敏感数据，存于操作系统安全存储，绑定到完成设置时登录的那个用户/服务器。
- **设置记录 (Setup record)**：本地「已完成设置」标记（非密），其存在使应用跳过向导直达主面板。会话凭据与设置记录在「成功设置」与「取消/失败清理」时必须保持一致的存在性。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户完整走完首次设置后到达主面板，期间**额外登录提示次数为 0**（全程仅在向导里输入一次凭据）。
- **SC-002**: 已设置且会话有效的返回用户重新启动客户端，**100%** 直接到达主面板、不出现登录框。
- **SC-003**: 在向导任一步取消后重启客户端，应用 **100%** 从设置第一步开始，本地不残留任何可用会话凭据。
- **SC-004**: 重新登录提示**仅**在会话确实失效（过期或被拒）时出现，正常有效会话下从不出现。

## Assumptions

- 复用客户端**既有的会话持久化与安全存储机制**（当前已在「面板内手动登录一次后」用于缓存会话的同一套），本切片只是把同样的保存动作提前到设置阶段，不引入新的存储介质。
- **纯客户端改动，无服务端变更**；会话的签发与有效期策略保持不变。
- 会话失效后的重新登录路径**已存在且保持不变**，本切片不改其行为。
- 「登录」与「创建账号」两条设置路径在认证完成后状态等价（创建账号在内部即「注册随后登录」），因此同一处会话持久化对两者都生效。
- 平台为 Windows 桌面客户端；安全存储指其操作系统凭据存储。
